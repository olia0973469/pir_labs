# CI/CD: нотатки та концепт наступного CD-кроку

## Що реалізовано (CI)

У проєкті налаштовано GitHub Actions workflow `MLOps CI` (`.github/workflows/mlops-ci.yml`). Він запускається при кожному `push` і `pull_request` у гілки `main` / `master` та виконує:

1. checkout репозиторію;
2. налаштування Python 3.11;
3. встановлення залежностей з `requirements.txt`;
4. перевірку синтаксису (`python -m compileall src app tests`);
5. запуск тестів (`pytest -q`);
6. валідацію даних (`src/validate_data.py`);
7. створення версії датасету (`src/version_data.py`);
8. smoke training (`src/train.py`);
9. збірку Docker-образу inference-сервісу.

Це Continuous Integration: після кожної зміни команда автоматично отримує сигнал, що проєкт і далі запускається, дані валідні, модель навчається, а образ збирається.

## Що не реалізовано (CD)

У цій роботі немає автоматичної доставки в середовище виконання. Pipeline лише перевіряє, що зміни «живі», але не публікує образ і не розгортає сервіс. Нижче описано, яким міг би бути наступний CD-крок.

## Можливі кроки CD

### 1. Публікація Docker-образу в registry

Після успішного CI образ збирається повторно й публікується в реєстр (GitHub Container Registry, Docker Hub або хмарний registry) з тегом, прив'язаним до commit (наприклад, `churn-api:<git-sha>`) та версією релізу. Це дає незмінний, відтворюваний артефакт, який можна розгорнути будь-де й до якого можна відкотитись.

### 2. Автоматичне оновлення staging-сервісу

Новий образ автоматично розгортається в staging-середовище, максимально схоже на production. Там виконуються:

- перевірка `/health`;
- тестовий запит до `/predict` з `examples/predict_request.json`;
- перевірка часу відповіді та відсутності помилок у логах.

Staging дозволяє виявити проблеми середовища до того, як вони вплинуть на користувачів.

### 3. Ручне approval перед production

Перехід у production потребує підтвердження відповідальної людини (наприклад, через GitHub Environments із required reviewers). Людина перевіряє результати staging, метрики моделі та зміни в даних. Для ML це особливо важливо, бо помилка моделі не завжди видна як технічний збій: сервіс може працювати, але давати гірші прогнози.

### 4. Перевірка метрик перед promotion моделі

Перед просуванням нової моделі в Model Registry (наприклад, присвоєнням alias `champion`) pipeline порівнює її метрики з поточною production-моделлю на однаковому наборі даних. Приклад правил:

- `recall` і `roc_auc` не нижчі за поточну модель (або за встановлений поріг);
- версія даних (`data_version`) та схема даних збігаються;
- валідація даних має статус `passed`.

Якщо умови не виконані, promotion блокується, а production продовжує використовувати попередню модель.

## Ризики автоматичного production deployment ML-моделі

- модель може мати кращі метрики на тестовій вибірці, але гірше працювати на реальних даних;
- дрейф даних: розподіл вхідних даних у production змінюється з часом;
- розбіжність preprocessing між навчанням та inference дає хибні прогнози без помилок;
- без ручного контролю та відкату помилкова модель швидко впливає на бізнес-рішення;
- автоматичний деплой без моніторингу не показує деградацію якості.

## Що додати до pipeline у реальному проєкті

- `ruff` для lint і форматування;
- перевірка порогів метрик як умова проходження pipeline;
- кешування залежностей та Docker-шарів для прискорення;
- запуск контейнера в CI та перевірка `/health` і `/predict`;
- сканування залежностей та образу на вразливості;
- публікація MLflow-артефактів і метрик у спільний tracking server;
- моніторинг якості моделі та дрейфу даних після розгортання;
- автоматичний відкат до попередньої версії.
